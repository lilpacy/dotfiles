# この状況、どう理解すればいいか

結論から言うと、一番危ういのは「モデルの挙動が一日中反転している」という捉え方そのものです。実際に反転しているのはモデルの挙動ではなく、**測定環境（fixture、グローバルskill、CODEX_HOME）の汚染源**で、しかもそれを毎回「3trialとも5/5だった／全trialでヒットした」という粒度でしか確認していません。これは知りたいこと（「without_skill は本当に goal-first 抜きか」）に対して、確認の仕方が一段粗すぎます。

## 一番弱い前提はどこか

> 隔離用CODEX_HOMEの中を`find`しても`goal-first`は見つからなかった。それでもgrepでヒットする。おかしい。

ここで「おかしい」と感じているのは、暗黙に **「goal-firstという文字列がログに出る経路は、`$CODEX_HOME/skills/goal-first`を読むことだけだ」** という前提を置いているからです。この前提自体を検証していません。`find`で確認したのは「その1つの経路が塞がれているか」だけで、「他に経路がないか」は確認していない。

しかも夕方に見つけた1つ目の汚染源（グローバルsymlink）は「たまたま見つかった」ものです。1つ見つけて塞いだら、まだヒットする——これは「まだ埋まっていない別の穴がある」と読むのが自然で、「原因不明の再発」と読むのは早計です。塞いだ穴の外側に何があるかを見ていないのに、塞いだ穴のことだけで頭がいっぱいになっている状態です。

## 次にやる、最も安くて情報量が高い一手

これまで一度も、**ヒットした行そのものを読んでいない**ことが最大の欠落です。`grep -io "goal-first" harness_log.txt | wc -l` 的な「件数」だけを見て、内容を見ずに「汚染された/されていない」を判定しています。まず1trialだけで良いので:

```
grep -n -B3 -A5 -io "goal-first" harness_log.txt
```

を実行して、ヒットしている行が次のどれかを見分けてください。

| ヒットの種類 | 見分け方 | 意味 |
|---|---|---|
| モデルの発言・思考の中で「goal-firstを適用します」的な文脈 | 会話ターンの本文中 | 本当にskillとして読まれ適用されている |
| 実行コマンド行やcwdのログ出力 | `codex exec --cd ...` や作業ディレクトリのパス表示 | fixtureパス自体に`goal-first`という文字列が含まれているだけ（誤検知） |
| プロンプト/タスクファイルの引用 | ユーザー入力やtask.mdの再掲部分 | プロンプト側に元々その語があり、モデルが単に引用している |

夕方に見つけた1回目の汚染は「モデルが明示的に『適用します』と言ってSKILL.mdを読みに行った」という、本文中の一次証拠がありました。今回はまだそれがない。もし今回のヒットが表の2番目（パスの再掲）だったなら、そもそも汚染ではなく、grepの検知ロジックが粗すぎたという別の話になります。件数のブレ（5〜17回、trialごとに違う）もこれを支持します——SKILL.mdを1回読むだけなら件数はファイルの内容に依存してほぼ一定になるはずですが、trialごとの手数（ターン数・ツール呼び出し数)に応じて件数が変わるなら、「ステップごとに作業パスをログに書いている」側が原因である可能性の方が高いです。

## それでも本当に汚染だった場合に確認すること

行の中身を見て「本当にモデルがskillを適用している」と分かったら、次に潰すべきは「CODEX_HOMEはグローバルなskill discoveryの経路しか塞いでいない」という可能性です。具体的には:

1. **その再実行で、実際にそのCODEX_HOME環境変数が該当のcodexプロセスに渡っていたか**を、ラッパースクリプトのコードを読むのではなく、実行時に確認する（例: 該当プロセスの起動直前に`env`をログに落とす、もしくは`/proc`相当で確認する）。「コード上そうなっているはず」と「実際そうだった」はここでは別問題です。
2. **fixtureの作業ディレクトリが、goal-firstをproject-scopeで公開しているリポジトリの内側にないか**を確認する。多くのコーディングエージェントはグローバルのホームディレクトリ設定に加えて、実行時のカレントディレクトリから上に遡ってプロジェクトローカルな設定・skillを探す仕組みを持っています。fixtureのコピー先がベンチマーク基盤のリポジトリ自身の内部にあると、CODEX_HOMEをどれだけ隔離しても、そのリポジトリがproject-scopeで公開しているskillをcodexが別経路で見つけてしまう、という抜け道が起こり得ます。朝の単発テストが「`/tmp`に隔離したfixture」で行われ、そこでは(結果は悪かったものの)goal-firstの影響が疑われていなかったのは、単にfixtureの位置がリポジトリの外だったからかもしれません。フルランのfixtureコピー先がどこかを、まず確認してください。

## 大きい推奨

いまの84ラン（medium/high×全モデル×2条件×3trial）の結果は、上記が片付くまで「参考値」として扱うべきです。同じ日に2つの独立した汚染源を後から発見しているという事実自体が、「without_skillは本当にskill抜きだ」という前提の検証が毎回甘かったことを示しています。次にやるべきは、フルランをもう一度回すことではなく、1trialだけ回して生ログを目で読み、汚染の経路を「これで確定」と言えるところまで特定することです。安い確認を先にせずに大きい再実行を重ねると、同じ穴を塞いだつもりで別の穴を踏むサイクルが続きます。
