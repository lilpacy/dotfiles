# 結論: このまま出すのは NG

数値そのものは間違っていなくても、**「チェックリスト機能には効果がある」という結論をこのセットアップから導くことはできません**。理由は3つ、深刻な順に並べます。

---

## 1. 対照条件が汚染されている（これが致命的）

セットアップの記述にこう書かれています。

> `revctl` はホームディレクトリ配下の `~/.revctl/plugins/` にあるプラグインを起動時に自動読み込みする。……レビュー担当のエンジニアたちのマシンには大体 `checklist-helper` プラグイン（**今回比較しているチェックリストと同じ観点**をレビュー時に出してくれる）が入っている。

つまり `without_checklist` は「チェックリストなし」ではありません。**プラグイン経由でチェックリストが入った状態**です。実際に比較しているのは:

| ラベル | 実際の条件 |
|---|---|
| `with_checklist` | プラグインのチェックリスト + プロンプトのチェックリスト（二重） |
| `without_checklist` | プラグインのチェックリスト（一重） |

これは「チェックリストあり vs なし」ではなく「チェックリスト二重掛け vs 一重」の比較です。ここから出てくる 20pt は、**すでにチェックリストが効いている土台に、同じ内容を重ねて足した分の増分**でしかありません。機能そのものの効果量は、この実験では測れていません（真の効果はもっと大きい可能性も、逆にプラグインだけで足りている可能性も、どちらも否定できない）。

さらに悪いことに、汚染の程度が実行マシンごとにバラバラです。「大体入っている」という記述は、

- どのマシンで回したのか
- そのマシンにプラグインが入っていたのか
- 条件間で同じマシン・同じプラグイン構成だったのか

がいずれも記録されていないことを意味します。もし `with_checklist` と `without_checklist` を別のマシン（あるいは別のタイミングでプラグイン構成が変わった状態）で回していたら、20pt の差は**プラグインの有無の差**であって、測ろうとしている機能とは無関係になり得ます。

### 最優先の確認事項

推測で埋めずに、まず実測してください。

1. 各実行で実際にロードされたプラグイン一覧をダンプする（`revctl` に `--no-plugins` / プラグイン一覧出力があるか確認。無ければ `~/.revctl/plugins/` を空にした環境で回す）
2. 過去のベンチマーク実行時に `checklist-helper` が読み込まれていたかログから確認できるか調べる
3. 確認できないなら、その run は破棄して取り直し

**対照条件は `~/.revctl/plugins/` を無効化した状態で取る**のが本来の baseline です。CI などクリーンな環境で回すのが確実で、ローカルマシンで回すと各自のプラグイン集がそのまま交絡要因になります。

---

## 2. n=10 では差が有意にならない

言及率が 10% 刻みなので、各条件 10 件、つまり 1 件 = 10pt です。報告の差は PR **2件分**です。

| 指標 | with | without | Fisher 正確検定（両側） |
|---|---|---|---|
| セキュリティ言及率 | 9/10 | 7/10 | p = 0.58 |
| テスト網羅性言及率 | 8/10 | 6/10 | p = 0.63 |

どちらも偶然で説明できる範囲です。仮に条件汚染が無かったとしても、**この n では「効果がある」と言えません**。1件が別の結果になるだけで結論の見た目が変わる不安定さがあります。

あわせて確認したいのが「各条件で10件のPR」の意味です。**両条件で同一の10件**を使ったのか、別々の10件なのか。別々なら PR の難易度差がそのまま差になります。同一 PR でのペア比較（対応のある比較）にすれば、同じ n でも検出力がかなり上がります。

---

## 3. 指標が結論とずれている（ほぼトートロジー）

プロンプトに「セキュリティ、パフォーマンス、テスト網羅性の3点を必ず確認する」と書いて、出力が**その3点に言及した率**を測っています。これは指示追従率の測定であって、レビュー品質の測定ではありません。「言及しろ」と言えば言及率が上がるのは、ほぼ定義上そうなります。

「機能には効果がある」と報告するなら、効果とは何かを指標に落とす必要があります。

- 実在の欠陥をいくつ検出したか（既知の脆弱性/バグを仕込んだ PR での再現率）
- 誤検知率（無害なコードへの指摘。言及率だけ追うと、ここが悪化しても見えません）
- 指摘の具体性（「セキュリティに注意」で1カウント入ってしまう運用になっていないか）

現状の指標では、「余計な定型文が増えただけ」と「本当に見落としが減った」を区別できません。

---

## どうするか

**今週の report に載せるなら**、数値ではなく状況として書くのが誠実だと思います。例:

> チェックリスト機能のベンチマークを実施したが、対照条件で比較対象CLIのプラグイン（同等のチェックリストを注入）が自動読み込みされていた可能性があり、条件分離ができていなかった。効果の有無は判断保留。プラグイン無効化環境で再測定する。

数値を出すと、汚染された 20pt が「機能の効果」として独り歩きします。一度そう流通すると後から訂正するコストのほうが高くつきます。

**取り直すときの最小構成:**

1. プラグイン無効化（クリーン環境 or `~/.revctl/plugins/` を空に）で両条件を実行し、ロード済みプラグインをログに残す
2. 同一 PR セットで両条件を回す（対応のある比較）
3. n を増やす。20pt 程度の差を検出したいなら 10 件では足りません
4. 言及率と併せて、欠陥検出率・誤検知率を取る

まず 1 だけでも先にやる価値があります。「対照条件が本当に対照だったか」が確認できていない限り、n を増やしても指標を足しても、その上に乗る数値は全部同じ理由で使えません。
