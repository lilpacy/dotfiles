結論から言うと、**このまま週次reportに載せるのは止めたほうがいい**です。数値が間違っているというより、この数値では「チェックリスト機能に効果がある」という主張を支えられません。理由は独立に2つあります。

## 1. 統制条件が統制されていない（これが致命的）

セットアップの記述にこう書かれています。

> `revctl` はホームディレクトリ配下の `~/.revctl/plugins/` にあるプラグインを起動時に自動読み込みする。（略）レビュー担当のエンジニアたちのマシンには大体 `checklist-helper` プラグイン（今回比較しているチェックリストと同じ観点をレビュー時に出してくれる）が入っている。

つまり `without_checklist` は「プロンプトにチェックリストを埋め込まなかった」条件であって、「チェックリストが無い」条件ではありません。プロンプト経路は閉じましたが、**プラグイン経路が開いたまま**です。しかも `checklist-helper` は今回測っているのと同じ観点（セキュリティ／テスト網羅性）を出すもので、測定指標そのものに直撃します。

これは without 側の 70% / 60% という数字がやや高いことと整合します。素のプロンプトだけで7割セキュリティに言及するというのは、そもそも「素」ではなかった可能性を示唆しています。この解釈が正しいなら、実測されているのは「チェックリストの効果」ではなく「プロンプト埋め込みがプラグイン由来のベースラインに上乗せする分」という別の量です。

重要なのは、**現時点ではどちらとも言えない**ことです。プラグインが入っていた証拠も、入っていなかった証拠も、まだ手元にありません。「埋め込まなかったから無いはず」は設計の意図であって、実行の証跡ではない。これは設定した自分を信じて証跡を確認していない状態です。

### 確認方法（実行ログを直接見る）

数分で終わります。まず実行環境に何が入っていたか。

```sh
ls -la ~/.revctl/plugins/
revctl --version && revctl plugins list   # ロード済みプラグイン一覧が出るなら
```

次に、`without_checklist` の生ログ（要約後の出力ではなく、stdout/stderr・ツール呼び出しログ）を機能名で grep します。

```sh
grep -rn -i -e checklist-helper -e 'checklist' path/to/without_checklist/raw_logs/
```

ここでプラグインのロード行や、チェックリスト由来の特徴的な文字列（プラグインが出力する定型句など）が1件でも出たら、without 側は汚染されています。

### 汚染されていた場合の測り直し

プラグインを一時的にアンインストールするのではなく、ホームディレクトリのスコープ自体を実行ごとに隔離するのが安全です。

```sh
HOME=$(mktemp -d) revctl review ...        # あるいは revctl が見るディレクトリを指す env var
# もし --no-plugins 相当のフラグがあるならそれでもよい
```

ただし**上書きしたら上書きが効いたことを同じ grep で確認する**まで完了ではありません。ここを飛ばすと、同じ「未検証の前提」を一段下で作り直すだけになります。加えて、この隔離は with 側にも同じく適用してください（with 側だけプラグインが乗っていると、今度は逆向きの差が入ります）。

## 2. n=10 では、この差は差と言えない

仮に統制条件がクリーンだったとしても、この差では結論を出せません。10件ずつなので、90% vs 70% は 9/10 vs 7/10、80% vs 60% は 8/10 vs 6/10 です。Fisher の正確確率検定で両側 p 値は

- セキュリティ言及率: p ≈ 0.58
- テスト網羅性言及率: p ≈ 0.63

いずれも偶然と区別がつきません。PR 1〜2件が違う挙動をしただけでこの差は消えます。「上がっている」ように見えるのは、単に標本が小さくてばらつきが大きいからかもしれません。20ポイント差を検出したいなら、必要な件数は桁で1つ多いオーダーです（power 80% を狙うなら各条件で概ね80件前後）。

## 併せて確認しておきたい点

- **同じPRを両条件で使ったか**、そして両条件で `revctl` の実行が互いに影響しない状態か。キャッシュや作業ディレクトリを共有していると、後の実行が前の実行の生成物を拾って、測ろうとしたステップ自体を飛ばすことがあります。試行ごとに使い捨てのディレクトリへ隔離するのが確実です。
- **「言及率」の判定基準**。人手判定なら、判定者が条件を知らない状態（ブラインド）でしたか。条件を知って読むと、with 側の曖昧な言及を拾いやすくなります。LLM判定・正規表現判定なら、両条件でまったく同じ判定器を通していますか。
- **両条件の計測経路が同じか**。片方は生ログ、もう片方は最終要約だけ、といった差があると、観測しているのは挙動の差ではなく「見えるものの差」になります。
- **with / without のプロンプト差分**。byte 単位で diff して、差がチェックリスト本文だけであることを確認してください（整形の都合で他の指示や順序も変わっていることは珍しくありません）。

## どうするか

1. まず `without_checklist` の生ログを1本 grep する。ここで結論の運命が決まるので、他より先にやる価値があります。
2. クリーンだった場合 → 統制条件は保たれているので、あとは件数を増やす話になります。
3. 汚染されていた場合 → ホームスコープを隔離して測り直し、隔離が効いたことを同じ grep で確認する。

なお、もし汚染が見つかって修正した場合でも、「プラグインを塞いだ」で調査を終わらせないでください。同じ症状（without 側が高く出る）を生む原因は他にもあり得ます（判定者の非ブラインド、実行間の状態共有、プロンプト差分の混入など）。原因を1つ見つけたことは、原因が1つだったことの証拠にはなりません。

今週どうしても何か出す必要があるなら、数値を載せる形にはせず「統制条件の検証中、`without` 条件に `checklist-helper` プラグイン混入の可能性あり。件数も n=10 で有意差なし（p≈0.6）。検証後に再測定して報告」と経緯だけ書くのが安全です。今の数値を「効果あり」として一度出してしまうと、後から撤回するコストのほうが高くつきます。

報告に載せる際は、統制条件が保たれていることを確認した**コマンドそのもの**（実行した grep とその結果）も併記してください。他の主張の根拠を示すのと同じ扱いで良いはずです。
