# 結論: まだクローズすべきではないです

「外部APIが一時的に重かった」は8/19の観測には確かに合いますが、**8/17の観測と両立しません**。最新の異常を説明できる仮説を見つけた時点で閉じると、変数を1つ取り逃がしたまま終わります。以下、気になった点を証拠ボードの形で整理します。

## 証拠ボード（これまで観測した「変なこと」の全リスト）

|---|------|------|-----------|------|
| E1 | 8/15 | ステージング1回、遅延**再現せず**（3分） | 環境差だろう | **未説明のまま放置** |

## 引っかかる点

### 1. プールサイズ5は「定数」なので、間欠的な症状の原因になり得ない（E3）

プールサイズは問題が起きる前からずっと5でした。遅延する実行と遅延しない実行の両方で5です。**変化しないものは、変化する症状を説明できません。** 説明できるのは「5だと、何か別の変動要因が加わったときに詰まる」までで、真の変動要因は特定できていない。プールを20にしたのは閾値を上げただけで、原因を消していない可能性が高いです。

さらに8/17の観測方法にサンプリングバイアスがあります。「遅延が起きた日のログを集めた」ので、遅延していない日にもプール待ちが出ていたかどうかが分かりません。遅延日だけを見て「3回ともプール待ち」は、プール待ちが原因だという証拠にはなりません。

### 2. E2 と E5 が正面から矛盾する

8/15にタイムアウトなしを見つけて直したのに、8/19に外部API応答待ちで7分固まっている。ここは3つのうちどれかです。

- **修正が本番に入っていない**（ステージングで直しただけ？）
- **タイムアウト値が7分より長い**（実質無限待ちと同じ）
- **修正したのと別の外部API呼び出し箇所**が詰まっている（＝箇所が複数ある）

どれであっても「外部APIが重かった」だけでは片付きません。タイムアウトが正しく効いていれば、p99が跳ねても7分は待てないはずです。**外部API側の遅さは引き金であって、7分に化けさせたのは自分たち側の設定です。**

### 3. 2つの症状を1つの原因で説明できる仮説がある（E3 + E5 を同時に説明）

「プール待ち」と「API応答待ち」を無関係な2つの原因として扱っていますが、**外部API呼び出しをDB接続を握ったまま実行している**なら、両方が同じ根本原因の別の見え方になります。

```
外部APIが遅くなる
  → API待ちの間もDB接続を返さない
  → 接続がプールに戻らない
  → 他のワーカーがプール待ちで固まる
```

この1本の仮説は、証拠ボードの全項目に整合します。

- E3（プール待ち）: プール5だと、数本が長時間握るだけで枯渇 → **プール待ちが先に見える**
- E4（20にしたら改善）: 枯渇しにくくなったので症状が消えた**ように見えた**
- E5（症状がAPI待ちに変わった）: 枯渇しなくなったので、**握っている本人の待ち時間がそのまま表に出た**
- E7（p99スパイク）: 引き金として整合

つまり症状が「プール待ち → API待ち」に変わったのは、原因が変わったからではなく、**プールを広げて症状を隠した結果、根本原因が素の形で露出した**という読み方ができます。現在の結論（無関係な2つの原因が偶然2日連続で別々に起きた）より、こちらのほうが単純です。

### 4. 「直った」判定に使った標本数が足りていない（E4, E6）

「たまに」起きる事象に対して、8/18の2回無遅延では何も言えません。仮に4回に1回遅延するなら、2回連続セーフは3割強の確率でただ起こります。8/19に3回中1回だけ遅延したのも同じで、**そもそも一度も「直った」は確認できていない**。8/19の再発は「直っていたものが別要因で壊れた」ではなく「最初から直っていなかった」で説明できます。

## 反証テスト（安いものから）

いま挙げた仮説を確定させるより先に、**自分の仮説を殺しにいく**確認を4つ。上2つはログを待たずに今すぐできます。

1. **コードを読む**: 外部API呼び出しがDB接続（トランザクション）を保持したまま行われていないか。1箇所読めば #3 が真か偽か決まる、いちばん安い決定的チェック。
2. **本番のタイムアウト設定を確認**: 8/15の修正が本番に入っているか、値は何秒か、外部API呼び出し箇所は本当に1つか。7分待てた事実と設定が合うか突き合わせる。
3. **反例を2つ探す**（ここが本題）:
   - **APIのp99が跳ねたのに遅延しなかった実行**があるか → あれば、APIの遅さは必要条件でしかなく、もう1つの変数がある
   - **遅延したのにAPIのp99が正常だった実行**があるか → あれば、独立した第2の原因が実在する
   - 特に **E6（8/19の遅延しなかった2回）** は同日同条件の対照群として一番手近です。この2回のときのAPI p99を見てください。
4. **母数を出す**: 直近の全実行の「所要時間 × API p99 × プール待ち時間」を1つの表にする。遅延日だけ見るのをやめる。8/17の3回のときAPI p99が上がっていたかどうかも、この表で分かります。

## 正直に言って、まだ説明できていないこと

- **E1**: 8/15にステージングで再現しなかった理由。「環境差」で片付けていますが、データ量・同時実行ジョブ・接続数のどれが違ったのか不明です。ここが分かれば、間欠性を生んでいる変動要因そのものが分かる可能性があります（現時点で候補: データ量、他ジョブとの同時実行、曜日による負荷、外部APIレイテンシ）。
- **「金曜だけ」の理由**: 週次処理・月末・データ量増など、金曜に固有の要因があるかは未確認です。外部APIのp99が跳ねた理由自体も外部要因と決めつけている状態で、こちら側の送信量が増えて相手を重くした、という向きも排除できていません。
- **第2の原因の有無**: #3 の仮説が正しくても、独立した第2の原因が同時に存在する可能性は消えません。テスト3で反例が出るかどうかで判断してください。

## 進め方の提案

プールサイズ20は戻さなくていいですが、**「プール待ちという分かりやすい警告灯を消した」状態**であることは記録に残してください。次に同じことが起きたとき、症状がまた別の場所に移動して混乱します。

チェック1と2は今日中に終わります。それでも仮説#3が否定され、テスト3で反例も出ないなら、そのときは「外部API起因、ただしタイムアウト未整備で被害が拡大」としてクローズできます。現状のまま閉じると、次の再発時にまた3日目からやり直しになります。
