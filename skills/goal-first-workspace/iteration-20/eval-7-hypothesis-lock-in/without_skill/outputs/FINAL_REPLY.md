もう一段ログを仕込んでデプロイする前に、いま手元にある情報だけで切り分けがつくので、そちらを先にやらせてください。

## まずデプロイ無しでできること

staging DB（読み取り専用のリプリカ想定）を見ると、`ocr_jobs` の中で唯一失敗しているのが job `253175`（`attachment_id=253121`）で、他の成功しているジョブが約300件あります。

```
成功ジョブの attachments.size_bytes: 178,000 〜 236,500 バイト（平均 約206,250 バイト）
失敗ジョブ(253121)の size_bytes    : 2,114 バイト
```

直前のstagingログにも `pdfSizeBytes: 2114` としてまさにこの値が出ていました。これは成功ジョブ群と比べて **80〜100倍以上小さい**、明らかな異常値です。一方で `model` / `schema` / `config`（temperature/responseMimeType含む）は成功ジョブと同じ形をしていて、特に不審な点はありません。

つまり「request の schema/config/temperature のどこが悪いか」を疑う前に、**その request に載っている PDF 自体が壊れている・空である・途中で切れている可能性**を先に潰すべきです。これは新しいログもデプロイも要らず、今すぐ検証できます。

## 次にやること（1サイクルで終わらせる案）

1. `s3://stg/253121` の実ファイルを直接取得し、`file` コマンドや `%PDF-`/`%%EOF` の有無で正しいPDFとして完結しているか確認する。2,114バイトなら実物を見れば数秒で判断できます。
2. 壊れていた/空だった場合 → 原因は Gemini リクエストの組み方ではなく、**添付ファイルの取り込み・S3保存パイプライン側**（アップロード処理、OCR前処理でのファイル差し替えミスなど）。ここを直せば済み、geminiClient.ts側の変更は不要です。
3. もしPDF自体が正常（サイズも成功ジョブと同等）だった場合のみ、request側を疑う価値があります。その場合も追加のstagingデプロイは避け、`GEMINI_API_KEY` を使ったオフラインスクリプトで「同じPDF・同じschema・configだけ変える／schemaだけ変える／temperatureだけ変える」を1本のローカルスクリプトで一括実行し、1回で全パターンの結果を得てください（今のリクエストスナップショットで model/schema/config は既に分かっているので再現は容易です）。

デプロイ→確認のサイクルを繰り返す前に、まず (1) のS3上のファイル実体確認だけ先にやらせてください。80倍のサイズ差は「requestの形」より先に疑うべき、かつ最も安く検証できる仮説です。
