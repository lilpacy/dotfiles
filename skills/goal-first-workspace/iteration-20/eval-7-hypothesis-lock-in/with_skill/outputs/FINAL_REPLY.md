## 結論: もう一段ログを仕込んでデプロイする前に、無料でできる確認があります。今それをやりました。

まず前提の確認です。今回のゴールは「schema/config/temperatureのどこが悪いかを切り分けるログを追加する」ことそのものではなく、「1回のデプロイ/確認サイクル(約1時間)で `ai_unavailable` の原因を特定する」ことだと理解しています。ここでもう一段ログ(4回目)を仕込んで様子を見るのは、これまでの「中途半端なログ→足りない→次のログ」というループをまさに繰り返す動きなので、その前に無料でできる検証を先にやりました。

### やったこと

ログに出ていた `pdfSizeBytes: 2114` が気になったので、staging DBの `attachments` / `ocr_jobs` を読み取り専用で確認しました。

```
job 253175 の attachment (id=253121): size_bytes = 2114
成功している job (300件) の attachment size: min=178,000 / max=236,500 / avg=206,250
```

**失敗しているジョブのPDFだけ、成功群より約100倍小さい外れ値です。** ログの `pdfSizeBytes: 2114` は attachments テーブルの値と一致しており、これはログ上の見かけ(たまたま小さいPDFを送った)ではなく、実際にそのサイズのファイルが保存されている、ということを意味します。

### これが意味すること

`schema` / `config`(temperature等) は3回のログ拡充で確認済みの通り「普通」に見えていて、実際 request 自体に問題があるようには見えません。一方で、2KB程度のファイルは請求書スキャンPDFとしては明らかに小さすぎ(成功群の1%程度)、壊れたPDF・空PDF・アップロード途中で切れたファイルである可能性が高いです。Geminiが `provider_error` で落ちているのは、request構造の問題ではなく「渡しているファイルが不正/空だから」という説明の方が、外れ値の大きさ(100倍)からしても筋が通ります。

### 次の一手(デプロイ不要)

もう一段ログを足す前に、s3の実物ファイルを直接確認してください。s3://stg/253121 (または本番の同等キー) をダウンロードし、以下を見るだけで切り分けが完了します:
- ファイルサイズが実際に2KB程度か
- PDFとして開けるか(ヘッダーが `%PDF-` か、ページ数、破損の有無)

これは1時間のデプロイサイクルを使わない、今すぐできる確認です。もしファイルが壊れている/空であれば、原因は「Geminiのrequest構成」ではなく「添付ファイルの取り込み・保存過程」側にあり、次の調査はそちらに向けるべきです。逆にファイルが正常な請求書PDFだった場合のみ、schema/config/temperatureを切り分ける次のログ(1回のデプロイで全部同時に取れるよう、最初から必要な情報を全部盛り込んだもの)を追加する価値があります。まずは前者を確認してから、必要なら後者に進むのが、1回のデプロイで済ませる最短路です。
