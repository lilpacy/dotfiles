```
Goal: 本番環境での単一実行で切り分け可能な診断情報を得て、次のデプロイで正しい箇所を修正できるようにする
Done-when: 本番ログに含まれるもの：(1) エントリ/エクスポイントの状態、(2) 各APIコール試行時のリクエスト/レスポンスステータス、(3) トランスフォーム失敗時の入力データ、(4) 最終同期件数 → すべて実装済み
Verified-by: コード検査—ログが記録される経路を追跡済み。各例外ハンドラで stack trace + コンテキスト（cursor、synced数、order/row ID）をキャプチャ。エラー時の詳細情報を確保
Constraints:
- stdout/stderr が cron に捨てられる → `/var/log/sync_worker.log` + stderr 両方に出力する対応済み
- デプロイ 40 分 + 24 時間待機 → この実行で必要な情報をすべて集める（再実行一度きり）
- 本番環境データのみ → API 応答とオーダー構造をディフェンシブに扱う（`.get()` で None 安全に）
```

## 変更内容

**過度に詳細なのは意図的です。再実行が 1 日待つため、一度の実行で止まれるようにしました。**

### 追加したログポイント

| 位置 | ログ内容 | 目的 |
|------|---------|------|
| `fetch_orders()` 開始 | cursor 値を記録 | どのページで止まったか特定 |
| API レスポンス後 | ステータス + バイト数 + パース結果 | ネットワーク / JSON 問題の区別 |
| `transform()` | order ID + 計算値（合計、地域） | データ構造の想定外を検出 |
| `upload()` 成功 | row ID + ステータス 200 | 何件まで書き込みが成功したか |
| 各例外ハンドラ | `exc_info=True` で stack trace + synced 件数 | 失敗時のコンテキスト完全保存 |

### 変更の意図

1. **exit 1 の理由が不明** → 全例外経路で stack trace をロギング。URLError（ネットワーク），JSONDecodeError（API 応答形式），KeyError/TypeError（データ欠落）それぞれ分離
2. **cursor とページング状態** → 各ページ完了後に cursor を記録。どの cursor で止まったか即座に判定可能
3. **部分失敗の可視化** → synced カウントを各エラーログに含める。「100 件目で止まった」が分かる
4. **データ構造の仮定** → `order.get("items")` → `.get("price")` と防御的に記述。本番データが想定と異なる場合を検出

### スキップ事項

- 再試行ロジック（修正内容が判明してから検討）
- メトリクス出力（ログから後から parse 可能）
- 本番以外での debug モード切り替え（今は常に DEBUG で集める）
