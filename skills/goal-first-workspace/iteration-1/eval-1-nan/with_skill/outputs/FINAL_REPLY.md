合計が NaN になる原因は `invoice.js` ではなく `utils.js` の `parseAmount` にありました。そちらを修正したので、`invoice.js` は 1 文字も変えずに直っています。

## 原因

`parseAmount` の実装が `parseFloat(s)` だけでした。

```js
function parseAmount(s) {
  return parseFloat(s);
}
```

`parseFloat("$1,200.50")` は先頭の `$` が数字として解釈できないため `NaN` を返します。`reduce` の中で `sum + NaN` が一度でも起きると、それ以降の合計はすべて `NaN` に伝播します。つまり `invoice.js` 側のロジックは最初から正しく、壊れていたのは共有の変換関数のほうでした。

## 修正内容

`utils.js` の `parseAmount` を、通貨記号・桁区切りカンマ・空白を取り除いてから数値化する実装に変えました。

```js
function parseAmount(s) {
  const cleaned = String(s).replace(/[$,\s]/g, "");
  if (!/^-?\d+(\.\d+)?$/.test(cleaned)) {
    throw new Error(`parseAmount: cannot parse ${JSON.stringify(s)}`);
  }
  return Number(cleaned);
}
```

ポイントは2つあります。

1つ目は、`invoice.js` ではなく `utils.js` を直したことです。`parseAmount` の呼び出し元を確認したところ、`invoice.js` のほかに `receipt.js` と `summary.js` も同じ関数を使っており、3つすべてが `NaN` になっていました。`invoice.js` の中だけでパース処理を書き換えると、報告された1件は直っても残り2件は壊れたままになります。共有関数を1か所直すほうが差分も小さく、根本原因への対処になります。

2つ目は、パースできない入力で例外を投げるようにしたことです。当初は不要な文字を除去して `Number()` に渡すだけの実装にしていたのですが、自己チェックを書いたところ `"abc"` のような文字列が空文字になり、`Number("")` が `0` を返してしまうことに気づきました。金額計算で不正な入力が黙って 0 になるのは `NaN` より危険です（合計が一見もっともらしい値になるため誤りに気づけない）。そのため数値形式を検証してから変換する形に改めました。

## 確認結果

3ファイルすべてを実行し、正しい合計が出ることを確認しました。

```
Invoice total: 1635.49
Receipt total: 38.5
Monthly summary: 7700.75
```

`invoice.js` は `1200.50 + 89.99 + 345.00 = 1635.49` で手計算と一致します。あわせて `parseAmount` 単体の assert チェック（桁区切りあり、マイナス金額、不正入力での例外）も通っています。

なお今回は入力が `$` 表記のみだったため、対応しているのは通貨記号・カンマ・空白の除去までです。`(40.00)` のような会計形式の負数表記や、小数点にカンマを使うロケール（`1.200,50`）が今後入ってくる場合は追加対応が必要になります。必要になったタイミングで声をかけてください。
