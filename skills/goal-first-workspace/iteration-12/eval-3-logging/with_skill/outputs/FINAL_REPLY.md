sync_worker.py にログ出力を追加しました。

## やったこと

cron が stdout/stderr を捨てているのが根本原因なので、ログを **ファイルに直接書き出す**ようにしました（`/tmp/sync_worker.log`、環境変数 `SYNC_WORKER_LOG_FILE` で変更可）。次回失敗時にこのファイルを見れば、今回のような「exit 1 しか分からない」状態を避けられます。

次の実行チャンスが今夜2:00の1回きり・デプロイに40分かかるという制約があるため、後から少しずつ足す前提ではなく、**この1回のデプロイで原因を特定できる情報を一度に埋め込み**ました:

- `fetch_orders` / `transform` / `upload` の各段階に try/except を追加し、失敗時に「どの段階で」「どのデータで」落ちたかをスタックトレース付きでログに記録
- HTTPError の場合はステータスコードとレスポンスボディも記録（API側の問題かデータ側の問題か区別できるように）
- `main()` にも全体を囲む try/except を追加し、「何件目まで正常に synced したか」を記録してから再 raise（exit code はそのまま 1 を維持するので、cron の失敗検知は変わりません)
- 開始・終了のログも追加し、そもそも今どこまで進んで落ちているか（起動直後か、途中か）が分かるようにしました

## 動作確認

ローカルでは本番データが無いため再現できませんが、`fetch_orders`/`upload` をモックに差し替え、2件目のオーダーで想定される欠損データ（`shipping` キー無し）から `transform` が例外を起こすケースを作って実行しました。

結果、ログファイルに以下が記録されることを確認済みです:
- どの関数で失敗したか（`transform failed order=...`)
- 失敗したオーダーの実際のデータ
- 完全なスタックトレース（`KeyError: 'shipping'`)
- 失敗までに何件 sync できていたか（`sync aborted after synced=1`)

これで今夜の実行が再度失敗した場合、`/tmp/sync_worker.log` を見るだけで「どのオーダー・どの処理段階で・どんなエラーで」落ちたかが一目で分かるはずです。exit code や既存の出力（`print(f"synced {synced} orders")`）はそのままなので、他の挙動は変えていません。
