## ゴールと達成条件

**ゴール**: 「ログを足す」ことではなく、**今夜2:00の1回の実行で落ちた原因を確定できること**。デプロイに40分かかり、実行チャンスは1日1回なので、「エラーコードだけ足す → 次の夜はメッセージも → その次はスタックトレース」という増分は 1回=1日 のコストになります。1パスで足りる情報量を最初から入れました。

**達成条件**: 今朝と同じ失敗が再発したとき、**追加デプロイなしで**「どのAPI呼び出し／どの注文レコードで、どの例外が、どの入力に対して起きたか」がログだけで分かる。

**結果**: 満たしています。壊れたレコードを1件混ぜた自己チェックを実行し、ログに `order failed ... order_id='bad-1' error=KeyError('address')` と生レコードとスタックトレースが出ることを確認済みです（`python3 sync_worker.py --self-check`）。

## 変更点

`sync_worker.py` のみ変更しました。

**1. cron が stdout/stderr を捨てる問題への対処（最重要）**

これが一番の障害でした。ログを足しても捨てられていたら意味がないので、stderr と**ファイルの両方**に出します。

```python
LOG_PATH = os.environ.get("SYNC_WORKER_LOG", "/var/log/sync_worker.log")
```

- レベルは意図的に **DEBUG** 固定。夜1回しか回らないので、出しすぎて読み飛ばすコストのほうが、足りずに1日待ち直すコストより安いです。
- `/var/log/` に書けない環境なら、cron 側で `SYNC_WORKER_LOG=/path/to/writable.log` を渡してください。開けなかった場合も落ちずに stderr へ警告を出します。

**2. HTTP エラーの本文を必ず記録**

`urllib` は `HTTPError` のレスポンス本文を明示的に `read()` しないと捨ててしまいます。「500だった」だけでは原因が分からないので、共通ラッパ `_request()` にまとめて、ステータス・URL・レスポンスヘッダ・本文（先頭2000字）・所要msを記録します。`fetch_orders` と `upload` の両方がここを通るので、片方だけ直して他方が無情報のまま、という状態にはなりません。あわせて **タイムアウト60秒** を入れました（これまで無期限で、ハングしていた場合は永久に待つ状態でした）。

**3. 1件の失敗で全体を止めない**

いま `transform` は `order["shipping"]["address"]["region"]` を無条件に辿るので、`address` 欠けの注文1件で `KeyError` を投げて全体が死にます。今朝の exit 1 の第一候補はこれです。1レコードで止めると「1件目の不正データしか分からない」ので、**失敗しても続行して不正レコードを全部集める**ようにしました。記録するのは、ページ番号・インデックス・order_id・例外・**注文の生JSON**・スタックトレースです。

失敗が1件でもあれば最後に **exit 1 を維持**します（成功扱いで静かに壊れるのを防ぐため）。

**4. 進行状況とページングの可視化**

ページごとに cursor・取得件数・レスポンスのキー・next_cursor と、終了時に合計件数・ページ数・失敗数・経過秒を出します。「どこまで進んで死んだか」が分かります。あわせて **cursor が進まない無限ループの検出**も入れました（`next_cursor` が同じ値を返し続けるケース。ハングしていたならこれも候補です）。

**5. 自己チェック**

`python3 sync_worker.py --self-check` で、正常1件＋`address` 欠け1件を流し、必要なログ行が実際に出ること・exit 1 になることを検証します。外部依存なし、フレームワークなしです。

## デプロイ前に確認してほしいこと

- **ログに顧客データが載ります。** 失敗レコードの生JSONとAPIレスポンス本文を記録するので、注文情報が `/var/log/sync_worker.log` に残ります。切り分けにはこれが決定的なのですが、社内の取り扱い規程に触れるなら、`_snippet()` をキー名のみ出力に絞るか、ログの保存先・保持期間を絞ってください。ここは私の判断だけで決められない部分です。
- **cron のリダイレクトも足しておくと安全です**: `>> /var/log/sync_worker.cron.log 2>&1`。ファイル出力とは独立した保険になります。

## 今夜の結果の読み方

朝いちで `grep -E 'ERROR|fatal|Traceback' /var/log/sync_worker.log` を見てください。

- `order failed ... KeyError` → データ起因。原因レコードが `order_raw` に出ています。`transform` を欠損許容にするか、API側のデータを直す判断になります。
- `HTTPError status=...` + 本文 → API側。ステータスと本文で切り分けられます。
- `URLError reason=...` / タイムアウト → ネットワークかハング。
- `cursor did not advance` → ページングのループ。

原因が確定したら実際の修正を入れます。ログはあくまで切り分け用なので、原因が分かった後はこの DEBUG 出力を INFO に落として整理するのが筋です。
